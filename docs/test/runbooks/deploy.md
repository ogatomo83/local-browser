# デプロイ手順

この文書では、変更をステージングと本番に出す手順をまとめています。
本番へのデプロイは、平日の 10 時から 16 時の間に行ってください。金曜の午後と祝日の前日は避けます。

## 前提条件

- プルリクエストがレビューで承認され、main ブランチに merge されていること。
- CI のテストがすべて通っていること。
- 表の形を変える変更 (マイグレーション) がある場合は、戻し方を事前に確認していること。

## ステージング

main ブランチに merge すると、自動でステージングにデプロイされます。手作業は要りません。
5 分ほどで反映されるので、次のことを確かめてください。

1. 変更した画面や API が、期待どおりに動くこと。
2. ステージングのダッシュボードで、エラー率が上がっていないこと。
3. QA の担当者に確認を依頼した場合は、その結果が出ていること。

## 本番デプロイ

本番には、リリース用のタグを打ってから、手動で承認して出します。

1. リリースタグを打つ。

   ```sh
   git switch main
   git pull
   git tag v1.2.3
   git push --tags
   ```

2. GitHub Actions の deploy-prod ワークフローが動き出すので、承認待ちの画面で内容を確かめて承認する。
3. Slack の #release チャンネルに「v1.2.3 を本番に出します」と書く。
4. デプロイが終わったら、ダッシュボードでエラー率と応答時間を 15 分間見る。
5. 問題がなければ、#release に「完了」と書く。

### 見るべき指標

| 指標 | 普段の値 | 要注意 | すぐ戻す |
|---|---|---|---|
| エラー率 | 0.1% 未満 | 0.5% 以上 | 2% 以上 |
| 応答時間 (遅いほうから 5%) | 300 ミリ秒 | 800 ミリ秒 | 2 秒 |
| DB の接続数 | 50 前後 | 150 | 上限の 200 |

## ロールバック

問題が見つかったら、迷わず一つ前のバージョンに戻します。原因の調査は戻したあとで構いません。

1. GitHub Actions で deploy-prod を開き、一つ前のタグを指定して再実行する。
2. #release と #incident に、戻したことと、その理由を書く。
3. DB マイグレーションを含むリリースだった場合は、表の形も戻す必要があるかを確かめる。戻す場合は [障害対応フロー](incident.html) に沿って、責任者の判断を仰ぐ。

マイグレーションで列を消した場合など、データが失われる変更は簡単には戻せません。
そのため、列を消す変更は「使わなくするリリース」と「実際に消すリリース」の 2 回に分けてください。

## よくある失敗

- タグを打つ前に main を最新にしておらず、古い内容が本番に出てしまった。
- 承認画面の内容を読まずに承認し、別の人の未確認の変更まで出てしまった。
- 金曜の夕方にデプロイし、週末に障害の対応をすることになった。
