障害対応フロー

サービスに障害が起きたときの動き方をまとめています。障害の重大度によって、最初にやることと連絡の早さが変わります。

迷ったら重いほうの重大度として扱ってください。あとから下げるのは簡単ですが、対応が遅れた時間は取り戻せません。

重大度の決め方

重大度状態の例最初の連絡報告の間隔
SEV1サービス全体が止まっている。決済ができない。5 分以内30 分ごと
SEV2一部の機能が使えない。動作がとても遅い。30 分以内1 時間ごと
SEV3見た目の崩れなど、利用者が回避できる問題。翌営業日なし

最初の 15 分

  1. Slack の #incident チャンネルに「障害対応を始めます」と書き、重大度を宣言する。
  2. SEV1 の場合は、責任者に電話をかける。夜間や休日でも構わない。
  3. 対応の指揮をとる人を 1 人決める。指揮をとる人は自分で作業をせず、状況の整理と連絡に専念する。
  4. ダッシュボードで、エラー率、応答時間、DB の接続数を確かめる。
  5. 直近にデプロイがあった場合は、まずロールバックを検討する。手順は デプロイ手順 を参照。

切り分けの観点

  • いつから起きているか。直近のデプロイや設定変更の時刻と重なっていないか。
  • すべての利用者に起きているか、一部だけか。特定の地域や端末に偏っていないか。
  • 外部のサービス (決済、メール配信など) の障害情報が出ていないか。
  • DB の接続数が上限に達していないか。遅い問い合わせが増えていないか。

復旧したあと

  1. #incident に復旧したことを書き、利用者向けのお知らせを取り下げる。
  2. 48 時間以内にポストモーテムを書く。テンプレートは共有ドライブにある。
  3. ポストモーテムでは、誰がやったかではなく、なぜ起きたか、どうすれば防げたかを書く。
  4. 再発防止の作業をチケットにし、担当者と期限を決める。
