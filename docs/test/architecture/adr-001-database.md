# ADR-001 データベースに PostgreSQL を採用する

- 状態: 承認済み
- 日付: 2026-04-01
- 決めた人: 基盤チーム (レビュー: 開発チーム全体)

## 背景

新しいサービスを作るにあたり、データベースを MySQL と PostgreSQL のどちらにするかを決める必要があった。
既存のサービスの一部は MySQL で動いており、運用の経験はそちらのほうが多い。
一方で、新しいサービスでは次のことが求められている。

- 商品の属性が商品ごとに異なるため、決まった形のない情報を柔軟に保存したい。
- 商品の説明文を全文検索したい。
- 将来、文の意味で似た商品を探す機能 (ベクトル検索) を入れる可能性がある。

## 検討した選択肢

| 観点 | MySQL 8 | PostgreSQL 16 |
|---|---|---|
| 形のない情報の保存 | JSON 型あり。索引の付け方に制約がある | JSONB 型あり。中身に索引を付けやすい |
| 全文検索 | あり。日本語には追加の設定が必要 | あり。日本語には拡張機能が必要 |
| ベクトル検索 | 標準ではなし | 拡張機能 pgvector で対応 |
| 社内の運用経験 | 多い | 少ない |
| クラウドのマネージドサービス | あり | あり |

## 決定

PostgreSQL 16 を採用する。

形のない情報を JSONB で扱えること、ベクトル検索を拡張機能で後から足せることが決め手になった。
運用の経験が少ない点は、マネージドサービスを使うことと、基盤チームが手順書を整えることで補う。

## 結果として起きること

良いこと:

- 商品の属性を、表の形を変えずに追加できる。
- ベクトル検索を入れるときに、別のデータベースを足さずに済む。

注意が必要なこと:

- MySQL 向けに書かれた既存のスクリプトは、そのままでは動かない。移行スクリプトを書く必要がある。
- 表の形を変える作業 (マイグレーション) のツールは sqlx-cli に統一する。チームごとに違うツールを使わない。
- バックアップと復元の手順を、本番に出す前に一度通しで試す。
